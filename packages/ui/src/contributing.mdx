# Contributing

How a component of the design system is written. Button is the reference implementation.

## Keep it simple

The simplest solution that meets today's needs wins. Simple code is easier to read, to review, to change and to fix in every instance at once.

- Build for a need the application has now, not one it might have later. A variant, a size, a prop, a token or a dependency is added when a screen needs it, not in advance: it is easier to add something than to remove it once pages depend on it.
- Prefer the platform: a native element, a CSS feature or a plain function before a library, a configuration or an abstraction.
- Prefer two plain components to one configurable component (`Button` and `LinkButton` rather than a polymorphic `Button`), and a little repetition to an abstraction made for a single case.
- Fewer options is a feature: every prop, variant and token is one more thing to document, test, check for accessibility and keep consistent.
- When a solution needs a long explanation, look for a simpler one first. When in doubt, leave it out.

## Before writing code

- The component has a guideline: when to use it, what the consumer provides, its rules. A new component, or a new prop, gets its guideline first.
- Every value comes from a token. When a design needs a value no token covers (a color, a size), the token is added to `src/theme.css` and to the [Tokens](?path=/docs/tokens--docs) page first.

## Files

- Components are grouped by role, the same groups as in the [Introduction](?path=/docs/introduction--docs): `actions`, `forms`, `display`, `feedback` and `navigation`.
- `src/components/<group>/<name>.tsx`: the component, named in kebab-case, one public component per file, with its parts when it is composed (see [Composition](#composition)). Private sub-components may live next to it.
- `src/components/<group>/<name>.stories.tsx`: its stories, titled `Components/<Group>/<Name>`, with the same examples as the guideline: every variant, every state, and the realistic use cases. Stories use generic English text ("Save", "Cancel", "Title"), not the application's content.
- `src/components/<group>/<name>.mdx`: its guideline, which is also its Storybook page. Once the component exists, the page attaches to its stories (`<Meta of={…} />`) and shows them with the props table, after the guideline (see `button.mdx`).
- The design system's other pages (foundations, guidelines) are `.mdx` files in `src/` too, each one next to the code it documents when there is some.
- The component, its parts and their props types are exported from `src/index.ts`.

## Comments

- Code says what it does; a comment says why, and only when the reason cannot be guessed by reading the code: an accessibility rule, a browser quirk, a constraint coming from elsewhere (`aria-disabled` rather than `disabled`, so that the button keeps the focus while loading).
- No comment that repeats the code, the name of a function or the type of a prop. When the code needs a comment to be understood, make the code clearer first.
- A comment that no longer matches the code is worse than none: it is updated or removed with the code it describes.

## Styles

- Styles are Tailwind classes, using only the design system's tokens. The linter rejects unknown classes, arbitrary values (`w-[13px]`, `bg-(--brand-600)`), arbitrary properties and the `dark:` variant: semantic tokens switch with the theme on their own.
- Variants are declared with `cva`, and conditional class lists are joined with `clsx()`, never with string concatenation.
- Classes are not merged: two classes that set the same property both stay on the element, and the stylesheet order decides which one applies. A component never produces two conflicting classes (a disabled state replaces the variant's colors instead of overriding them).
- `className` is accepted on the root element, for layout only (margins, width, grid placement): it cannot reliably override the component's own styles.
- The formatter sorts classes (inside `className`, `clsx()` and `cva()`).
- The linter and the formatter only see classes inside `className`, `clsx()` and `cva()`. A class list kept in a variable (to share it between variants, for example) is wrapped in `clsx()`: `const interactive = clsx('cursor-pointer active:scale-98')`. A plain string is neither checked nor sorted.

## Props

- Props extend the props of the rendered element (`ComponentProps<'button'>`) and are passed through to it, so that `id`, `aria-*`, `data-*`, event handlers and `ref` work as on the native element. React 19 passes `ref` as a regular prop: no `forwardRef`.
- Prop names follow the guideline, and HTML names when they exist (`disabled`, `checked`, `value`), never an alias.
- Stateful components are controlled (`value` + `onChange`, `checked` + `onChange`…) or uncontrolled (`defaultValue`, `defaultChecked`…), with the HTML names: a form library that registers native inputs relies on the uncontrolled form.
- Booleans default to `false` and are named after the non-default state (`disabled`, `loading`, `optional`).
- Icons are passed as concept names (`icon="send"`), never as elements.
- Components contain no text of their own: every word shown or read by a screen reader (a close button's name, "Step 2 of 3") is a prop, written in the application's language by the consumer.
- No `asChild` or polymorphic `as` prop: a component that can also be a link comes as a second component that renders an `<a>` (`Button` and `LinkButton`), sharing its styles.

## Composition

A component that has more than one content area, or whose content the consumer arranges, comes as a set of small parts rather than as props that hold content (`title`, `actions`, `footer`, `items`…):

```tsx
<Dialog open={open} onClose={close}>
  <DialogContent closeLabel="Close">
    <DialogHeader>
      <DialogTitle>Delete the item?</DialogTitle>
      <DialogDescription>It cannot be undone.</DialogDescription>
    </DialogHeader>
    <DialogFooter>…</DialogFooter>
  </DialogContent>
</Dialog>
```

- An atomic control (`Button`, `Input`, `Checkbox`, `Badge`…) stays a single component.
- Parts are exported flat, named after the component (`DialogTitle`, not `Dialog.Title`), and live in the component's file.
- Each part follows the rules of [Props](#props): it extends the props of the element it renders, and passes `className` and the other props through.
- The parts share their state through Ark's context (Dialog, Tabs, Field, Fieldset…), or through a React context of the component when Ark has none.
- What accessibility needs is kept in a required part, so that leaving out an optional part cannot break it: the close button of a dialog is part of `DialogContent`, which requires its name.
- The guideline lists the parts, which ones are required and in which order they go.
- `Field` is the only component that also comes as a shortcut (`<Field label hint error>`), built from its parts, for the common case of a field.

## Behavior and accessibility

- Components are built on [Ark UI](https://ark-ui.com/react) as much as possible, the interactive ones (Dialog, Tabs, Switch, RadioGroup, Checkbox, Select, Toast…) and the form structure alike (`Field` for a field's label, hint and error, `Fieldset` for a group): focus management, keyboard navigation, ids and ARIA come from it, and the component only adds the design system's rendering. The rendering is styled through Ark's `data-*` state attributes (`data-state="checked"`, `data-disabled`…).
- A plain element (`<button>`, `<a>`) stays native when Ark has no part for it.
- Every guideline rule about accessibility is implemented, not left to the consumer: accessible names, links to hints and errors, announcements, focus return.
- Check each story with the keyboard only, and at 200% zoom.
